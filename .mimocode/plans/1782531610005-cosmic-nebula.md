# 记忆库与业务层解耦重构方案

## 背景

当前记忆库（source_data / knowledge_chunks / LanceDB）与业务层高度耦合：
- 业务删除命令直接操作 source_data、vector_cache、LanceDB
- 业务表通过 SQLite 触发器同步写入 source_data（每种业务 50-100 行 SQL）
- 全局搜索直接查询 source_data_fts，业务标题补全逻辑混在记忆库层

目标：业务层与记忆库完全解耦，通过接口通信。

## 架构设计

### 三个接口

| 操作 | 接口 | 业务层知道什么 |
|------|------|--------------|
| 写入 | `notify_changed(type, id)` | 只知道要通知 |
| 删除 | `notify_deleted(type, id)` | 只知道要通知 |
| 读取 | 双路检索（业务表 + source_data） | 前端去重 |

### 数据流

```
写入：业务表 INSERT/UPDATE → notify_changed → 记忆库异步提取 → source_data → chunks → LanceDB
删除：业务表 DELETE → notify_deleted → 记忆库异步清理 → source_data → chunks → LanceDB
读取：Header 搜索 → 业务表检索 + source_data FTS5 → 前端合并去重
```

## 实施步骤

### Phase 1：删除解耦

**目标**：业务层不再直接操作 source_data / vector_cache / LanceDB

**修改文件**：
- `src-tauri/src/services/knowledge_lifecycle.rs` — 新增，统一接口
- `src-tauri/src/services/cleanup_pipeline.rs` — 内部化
- `src-tauri/src/commands/file_commands.rs` — 内部调用改为 notify_deleted
- `src-tauri/src/commands/project_commands.rs` — 替换为 notify_deleted
- `src-tauri/src/commands/product_commands.rs` — 同上
- `src-tauri/src/commands/notes_commands.rs` — 同上
- `src-tauri/src/commands/todo_commands.rs` — 同上

**步骤**：

1. 新增 `src-tauri/src/services/knowledge_lifecycle.rs`：
   ```rust
   pub fn notify_deleted(source_type: &str, source_id: &str) {
       cleanup_pipeline::enqueue_cleanup(source_type, source_id);
       cleanup_pipeline::wake_cleanup();
   }
   pub fn notify_changed(source_type: &str, source_id: &str) {
       // Phase 2 实现
   }
   ```

2. 重构 `cleanup_pipeline.rs`：
   - `enqueue_cleanup` 改为 `pub(crate)`
   - `wake_cleanup` 改为 `pub(crate)`
   - 其余逻辑不变

3. 业务删除命令改为调用 `notify_deleted`

4. `file_commands.rs` 内部的 `cleanup_kb_for_file` 调用改为 `notify_deleted("FILE", fid)`

5. 移除 `cleanup_orphan_files_for_entity`（空函数，死代码）

### Phase 2：写入解耦

**目标**：移除 SQLite 触发器，改为事件驱动写入

**修改文件**：
- `src-tauri/src/database.rs` — 移除 `init_struct_source_data_triggers`
- `src-tauri/src/services/knowledge_lifecycle.rs` — 实现写入队列 + 数据提取
- `src-tauri/src/services/source_doc_sync.rs` — 重构为从队列消费
- `src-tauri/src/commands/kb_commands.rs` — CHAT 写入改用 notify_changed

**步骤**：

1. `knowledge_lifecycle.rs` 新增写入队列：
   ```rust
   pub fn notify_changed(source_type: &str, source_id: &str) {
       // 入队，由 knowledge_pipeline 异步处理
       enqueue_sync(source_type, source_id);
   }
   ```

2. 实现数据提取函数（替代触发器逻辑）：
   ```rust
   fn extract_source_data(source_type: &str, source_id: &str) -> Option<(String, String)> {
       // 根据 source_type 查询业务表，返回 (title, content)
       // 替代 19 个触发器的 SQL 拼接逻辑
       match source_type {
           "NOTE" => { /* 查询 notes 表 */ }
           "PRODUCT" => { /* 查询 products 表 */ }
           "PROJECT" => { /* 查询 projects 表 */ }
           "TODO" => { /* 查询 todos 表 */ }
           "FILE" => { /* 查询 file_relations 获取 custom_name 拼接 */ }
           "CHAT" => { /* 从 chat_sessions 获取 */ }
           _ => None
       }
   }
   ```

3. 业务写入命令（create/update）在操作完成后调用 `notify_changed`

4. `kb_commands.rs` 中 CHAT 写入（第 238 行）改为调用 `notify_changed("CHAT", &id)`

5. 数据库初始化时不再创建 `sd_notes_insert`、`sd_products_insert` 等写入触发器

6. 保留 `sd_chunks_delete` 触发器（source_data 删除时级联删除 knowledge_chunks）

### Phase 3：读取解耦（Header 全局搜索）

**目标**：Header 搜索走双路检索，前端去重

**修改文件**：
- `src-tauri/src/commands/kb_commands.rs` — 新增双路检索接口（保留 kb_memory_objects 作为过渡）
- `src/renderer/src/api/db-client.ts` — 新增 searchBusiness + searchSourceData
- `src/renderer/src/components/layout/Header.vue` — 实现双路检索

**步骤**：

1. 后端新增业务表检索接口：
   ```rust
   #[tauri::command]
   pub async fn search_business(query: String) -> Result<Value, String> {
       // 模糊匹配 projects.name, products.name, notes.title, file_relations.custom_name
       // 返回 [{source_type, source_id, title}]
   }
   ```

2. 后端新增 source_data 检索接口：
   ```rust
   #[tauri::command]
   pub async fn search_source_data(query: String) -> Result<Value, String> {
       // FTS5 检索 source_data
       // 返回 [{source_type, source_id}]
   }
   ```

3. 前端双路检索（Header.vue）：
   ```typescript
   async function globalSearch(query: string) {
       const [business, sourceData] = await Promise.all([
           searchBusiness(query),
           searchSourceData(query)
   ```

4. 验证通过后，移除旧的 `kb_memory_objects` 接口

### Phase 4：清理遗留

**步骤**：

1. 移除 database.rs 中的 `init_struct_source_data_triggers` 函数
2. 移除 file_commands.rs 中的触发器创建代码（第 50-55 行）
3. 清理 `cleanup_orphan_source_data` 兜底逻辑（保留但简化）
4. 更新 `kb_memory_objects` 为新的双路接口
5. 确认所有业务命令都走 `notify_changed` / `notify_deleted`
